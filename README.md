# Web Data Pipeline — параллельный сбор и индексация веб-данных на Go

Практический пример backend-сервиса на Go, который превращает список URL в структурированный поток данных: параллельно загружает веб-страницы, извлекает информацию, сохраняет результаты в PostgreSQL и индексирует их в Elasticsearch.

Проект показывает, как построить небольшой, но приближенный к реальной задаче pipeline обработки веб-данных с контролируемой параллельностью, сохранением результатов и быстрым поиском.

## Что можно получить из этого проекта

Если вы изучаете Go или проектируете backend-сервисы, репозиторий можно использовать как практический пример нескольких инженерных решений:

* понять, как организовать **Worker Pool** для параллельной обработки большого количества задач;
* ограничить количество одновременно выполняемых HTTP-запросов и не перегружать систему;
* построить **Crawler**, который обрабатывает страницы и найденные ссылки;
* организовать безопасную передачу результатов между горутинами через channels;
* корректно завершать несколько горутин с помощью `sync.WaitGroup`;
* разделить загрузку, обработку и сохранение данных;
* сохранять исходные результаты обработки в PostgreSQL;
* индексировать собранные данные в Elasticsearch;
* использовать Elasticsearch для быстрого поиска и дальнейшей агрегации;
* посмотреть на структуру Go-проекта с разделением на `cmd`, `internal` и `pkg`;
* увидеть пример работы с конфигурацией, логированием, миграциями и тестами;
* запустить всю инфраструктуру локально через Docker Compose.

Таким образом, проект полезен не только как пример веб-скрапера. Его можно рассматривать как основу для сервисов, которым необходимо **параллельно получать данные из внешних источников, сохранять их и предоставлять быстрый доступ к результатам**.

## Как работает проект

Общий поток данных выглядит так:

```text
                    ┌─────────────────┐
                    │      URLs       │
                    │   PostgreSQL    │
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │     Crawler     │
                    │   получение URL │
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │   Worker Pool   │
                    │                 │
                    │ Worker 1        │
                    │ Worker 2        │
                    │ Worker 3  ...   │
                    └────────┬────────┘
                             │
                    Fetch → Parse
                             │
                             ▼
                    ┌─────────────────┐
                    │ ScrapeResult    │
                    └────────┬────────┘
                             │
                   ┌─────────┴─────────┐
                   ▼                   ▼
          ┌─────────────────┐  ┌─────────────────┐
          │   PostgreSQL    │  │  Elasticsearch  │
          │                 │  │                 │
          │ pages           │  │ pages_index     │
          │ results         │  │                 │
          │ urls            │  │ поиск / анализ  │
          └─────────────────┘  └─────────────────┘
```

Главная идея — отделить получение данных от их сохранения.

Worker Pool выполняет сетевую и CPU-bound работу, а отдельная горутина получает готовые результаты и записывает их в PostgreSQL.

## Worker Pool и конкурентная обработка

Основной механизм параллельной обработки построен вокруг Worker Pool.

Вместо последовательной обработки:

```text
URL 1 → Fetch → Parse → Save
URL 2 → Fetch → Parse → Save
URL 3 → Fetch → Parse → Save
```

задачи распределяются между несколькими workers:

```text
              ┌── Worker 1 ──→ Fetch → Parse ──┐
URLs ────────►├── Worker 2 ──→ Fetch → Parse ──┤
              ├── Worker 3 ──→ Fetch → Parse ──┤
              └── Worker N ──→ Fetch → Parse ──┘
                                                │
                                                ▼
                                           results chan
```

Количество одновременно работающих workers можно контролировать.

Это позволяет использовать параллельную обработку без создания неограниченного количества горутин и HTTP-запросов.

## Как организовано завершение горутин

Функция `Run` использует две основные горутины:

1. **Submitter** — отправляет URL в Worker Pool.
2. **Writer** — получает результаты и сохраняет их в PostgreSQL.

Схематично:

```text
                         Run
                          │
              ┌───────────┴───────────┐
              │                       │
              ▼                       ▼
        Submitter                  Writer
              │                       │
              ▼                       │
         Worker Pool                   │
              │                       │
       Fetch → Parse                  │
              │                       │
              ▼                       │
        results chan ────────────────►│
                                      │
                                      ▼
                              SaveResult
                              SavePage
```

Последовательность завершения:

```text
Submit URLs
    ↓
pool.Close()
    ↓
Workers завершили работу
    ↓
close(results)
    ↓
Writer дочитал results
    ↓
wg.Wait()
    ↓
Run завершён
```

Такой порядок важен: канал `results` закрывается только после того, как Worker Pool закончил выполнение всех задач.

## PostgreSQL

PostgreSQL используется как постоянное хранилище результатов работы scraper.

В проекте предусмотрены таблицы:

* `urls` — исходные URL;
* `results` — результаты обработки;
* `pages` — обработанные страницы.

Исходный контент также может сохраняться в `results`, поэтому PostgreSQL можно использовать как хранилище исходных данных, к которым можно вернуться после завершения scraping.

### Пример результатов

```sql
SELECT * FROM pages;
```

## Elasticsearch

После получения результата данные могут индексироваться в Elasticsearch.

Используется индекс:

```text
pages_index
```

Это позволяет отделить задачу хранения исходных данных от задачи быстрого поиска и анализа.

Например:

```text
Go scraper
     │
     ▼
ScrapeResult
     │
     ├──────────────► PostgreSQL
     │
     └──────────────► Elasticsearch
                            │
                            ▼
                       поиск / агрегации
```

![Elasticsearch / Kibana](screenshots/kibana1.png)

### Что происходит при индексации

`models.ScrapeResult` сериализуется в JSON и отправляется в Elasticsearch.

При этом:

* выбирается индекс `pages_index`;
* `result.URLID` используется как ID документа;
* применяется `WithRefresh("wait_for")`;
* используется кастомный routing;
* timeout операции ограничен 5 секундами;
* ошибки индексации возвращаются вызывающему коду.

Routing рассчитывается следующим образом:

```text
result.URLID % 5
```

Это демонстрирует возможность явно управлять маршрутизацией документов по шардам Elasticsearch.

## Что здесь можно использовать в своих проектах

### Для Go-разработчика

Можно взять реализацию Worker Pool и адаптировать её под задачи, где необходимо обработать большое количество независимых операций:

```text
очередь задач
     ↓
Worker Pool
     ↓
параллельная обработка
     ↓
результаты
```

Например:

* обработка файлов;
* HTTP-запросы;
* обработка сообщений;
* фоновые задачи;
* импорт данных;
* batch processing.

### Для backend-разработчика

Проект показывает вариант разделения приложения на несколько независимых компонентов:

```text
HTTP Client
     ↓
Scraper
     ↓
Worker Pool
     ↓
Result
     ├── PostgreSQL
     └── Elasticsearch
```

Такой подход можно использовать как основу для сервисов сбора и обработки данных.

### Для изучения конкурентности в Go

Проект является практическим примером работы с:

* goroutines;
* channels;
* `sync.WaitGroup`;
* ограничением конкурентности;
* жизненным циклом Worker Pool;
* синхронизацией завершения нескольких компонентов.

## Запуск

### Требования

* Go 1.18+
* Docker / Docker Compose
* PostgreSQL
* Elasticsearch
* интернет-доступ для получения веб-страниц

### 1. Клонировать проект

```bash
git clone <repository-url>
cd <repository-directory>
```

### 2. Подготовить конфигурацию

Скопировать пример переменных окружения:

```bash
cp .env.example .env
```

При необходимости изменить параметры подключения к PostgreSQL и Elasticsearch.

### 3. Запустить инфраструктуру

```bash
docker compose up -d
```

### 4. Запустить приложение

```bash
go run cmd/scraper/main.go
```
